# Заметки по HID-протоколу

Windows-доступ к HID находится в [src/platform/windows/hid.rs](../src/platform/windows/hid.rs),
переносимые типы данных — в [crates/core/src/model.rs](../crates/core/src/model.rs),
кодирование разрешённых запросов чтения — в [crates/core/src/protocol.rs](../crates/core/src/protocol.rs).

Этот документ фиксирует проверенное поведение HID, которое использует tray-утилита, и безопасные направления для будущих доработок.

## Область применимости

Проверенные интерфейсы Ninjutso Ten на этой машине:

```text
VID_093A&PID_EB01  беспроводной приёмник
VID_093A&PID_E020  мышь, подключённая по USB (REV_1613)
```

И приёмник, и подключённая по USB мышь видны в системе как составные HID-устройства с несколькими HID-коллекциями. Не каждая коллекция принимает vendor feature report. Поэтому утилита перечисляет все доступные HID-интерфейсы и пробует только пути, содержащие один из проверенных идентификаторов:

```text
vid_093a&pid_eb01
vid_093a&pid_e020
```

На момент проверки рабочая коллекция для батареи выглядела примерно так:

```text
\\?\hid#vid_093a&pid_eb01&mi_02&col06#...\{4d1e55b2-f16f-11cf-88cb-001111000030}
```

Точный instance id между `#` может меняться между машинами, USB-портами, донглами или состояниями спаривания. `mi_02&col06` полезно воспринимать как подсказку для приёмника, но не как жестко заданный адрес. У проводного `PID_E020` Windows также создаёт несколько vendor-defined коллекций на `MI_02`, поэтому для него действует тот же перебор путей.

## Как устроен доступ через Win32

Rust-приложение использует прямой FFI к стандартным Windows API:

- `HidD_GetHidGuid` из `hid.dll`;
- `SetupDiGetClassDevsW`, `SetupDiEnumDeviceInterfaces`, `SetupDiGetDeviceInterfaceDetailW`, `SetupDiDestroyDeviceInfoList` из `setupapi.dll`;
- `CreateFileW` и `CloseHandle` из `kernel32.dll`;
- `HidD_SetFeature` и `HidD_GetFeature` из `hid.dll`.

HID-путь открывается с такими параметрами:

```text
DesiredAccess: GENERIC_READ | GENERIC_WRITE
ShareMode:     FILE_SHARE_READ | FILE_SHARE_WRITE
Disposition:   OPEN_EXISTING
Attributes:    FILE_ATTRIBUTE_NORMAL
```

Некоторые подходящие HID-пути возвращают `Access denied` или `Invalid function`. Для составных HID-устройств это нормально. Текущая реализация пробует найденные пути по очереди, пока один из них не вернет ожидаемый echo команды.

## Формат feature report

Все проверенные команды отправляются в 16-байтовом feature report. Ответ может
не содержать хвостовые нули: при проверке проводного `PID_E020` на Debian 13
через VMware 17.11.2026 scalar-команды вернули 9 байт, GET DPI — 10 байт.
Поэтому проверяются report ID, echo команды и наличие всех байтов значения,
а не обязательная длина 16. Недостающие байты самого значения недопустимы.

Linux выбирает только vendor-коллекцию `usage page 0xFF01 / usage 0x0001`,
в которой объявлен feature report `0x06`. Клавиатурные, мышиные и consumer-control
коллекции для обмена телеметрией не используются. Один hidraw-путь может быть
перечислен HIDAPI несколько раз для разных коллекций.

Буфер запроса перед `HidD_SetFeature`:

| Индекс байта | Значение | Смысл |
| --- | --- | --- |
| `[0]` | `0x06` | HID report ID |
| `[1]` | command | vendor-команда |
| `[2]` | `0x00` | не используется в проверенных командах |
| `[3]` | `0x00` | не используется в проверенных командах |
| `[4]` | `0x01` | request marker, который ожидает устройство |
| `[5]` | `0x00` | ноль для запросов чтения |
| `[6]` | `0x01` / `0x00` | одно значение для GET DPI (`0x04`); ноль для остальных запросов |
| `[7]` | profile / `0x00` | профиль для `0x04`, `0x06`, `0x1C`; ноль для остальных запросов |
| `[8]` | stage / `0x00` | уровень DPI для `0x04`; ноль для остальных запросов |
| `[9..15]` | `0x00` | не используется в запросах чтения |

Последовательность чтения:

1. Заполнить 16-байтовый буфер запроса.
2. Вызвать `HidD_SetFeature(handle, request, 16)`.
3. Подождать примерно 30 мс.
4. Заполнить 16-байтовый буфер ответа нулями и поставить `response[0] = 0x06`.
5. Вызвать `HidD_GetFeature(handle, response, 16)`.
6. Проверить report ID `response[0] == 0x06` и echo `response[1] == command`.
7. Читать полезное значение из `response[8]`.

В проверенных battery reports также встречался `response[6] = 0x01`, но текущая утилита на этот байт не опирается.

## Проверенные команды

| Команда | Decimal | Смысл | Текущий парсер |
| --- | ---: | --- | --- |
| `0x04` | 4 | DPI указанного уровня профиля | `(u16_le(response[8..10]) + 1) * 50`, только Ten |
| `0x06` | 6 | частота опроса выбранного профиля | профиль в request `[7]`; код из response `[8]` |
| `0x10` | 16 | активный профиль | response `[8]` |
| `0x11` | 17 | статус зарядки | `response[8] != 0` |
| `0x12` | 18 | процент заряда | `response[8]`, ожидаемо `0..=100` |
| `0x13` | 19 | online-статус | `response[8] == 1` |
| `0x1C` | 28 | активный уровень DPI в профиле | response `[8]`, индексы `0..=3` |

Текущий путь в Rust-коде:

```text
read_mouse_battery()
  enumerate_hid_paths()
  сначала пробует PID_E020 (USB), затем PID_EB01 (приёмник)
  query_battery_path(path, connection_kind)
    query_feature(path, ReadRequest::Online) -> online
    query_feature(path, ReadRequest::Battery) -> battery percent
    query_feature(path, ReadRequest::Charging) -> charging state
    если online, необязательно:
      query_feature(path, ReadRequest::ActiveProfile) -> profile
      query_feature(path, ReadRequest::PollingRate { profile }) -> polling rate
      query_feature(path, ReadRequest::ActiveDpiStage { profile }) -> stage
      query_feature(path, ReadRequest::DpiStage { profile, stage }) -> DPI
```

Проводной интерфейс проверяется первым, потому что при одновременно вставленном приёмнике USB-подключение даёт наиболее прямое состояние мыши. Если рабочий report отвечает, но `online == false`, результат сохраняется как fallback; утилита продолжает искать online-интерфейс.

## Пример сырых ответов

Снято 2026-07-04 при заряде 93%, мышь online, не заряжается:

```text
Online:  06 13 00 00 00 00 01 00 01 00 00 00 00 00 00 00
Battery: 06 12 00 00 00 00 01 00 5D 00 00 00 00 00 00 00
Charge:  06 11 00 00 00 00 01 00 00 00 00 00 00 00 00 00
```

Расшифровка:

- `0x13` вернулась echo в байте `[1]`, байт `[8] = 0x01`, значит мышь online;
- `0x12` вернулась echo в байте `[1]`, байт `[8] = 0x5D`, decimal `93`, значит заряд 93%;
- `0x11` вернулась echo в байте `[1]`, байт `[8] = 0x00`, значит зарядка не идет.

## Проверка проводного режима

Снято 2026-07-16 при подключении Ninjutso Ten кабелем:

```text
PID:       E020
Battery:   100%
Online:    true
Charging:  true
```

Установленный NinjaForce 1.0.7 был дополнительно проверен как источник протокола. В его ресурсах `57376` (`0xE020`) указан среди проводных PID, а чтение заряда, процента и online-статуса выполняется теми же командами `17`, `18` и `19` с полезным значением в байте `[8]`. То есть поддержка USB в tray-утилите использует штатный read-only путь устройства, а не неизвестную vendor-команду.

## Частота опроса

Чтение сверено с установленным NinjaForce 1.0.8: методы `getPrf()` и
`getRepRate()` в `out/renderer/assets/index-VPYasxOu.js`. SHA-256 этого модуля:
`f709c31c3ff07b69a9ee4f2b1f562b48d5853f3b9a2b9c804e9111fce9108dab`.
Те же getter-запросы обнаружены в ранее установленном модуле `index-CJvW9W26.js`.
Это сведения о протоколе; исходники приложения производителя в репозиторий не включаются.

Для профиля 1 запросы целиком, включая report ID:

```text
Active profile: 06 10 00 00 01 00 00 00 00 00 00 00 00 00 00 00
Polling rate:   06 06 00 00 01 00 00 01 00 00 00 00 00 00 00 00
```

Номер профиля для второго запроса всегда берётся из свежего ответа первого,
а не из настроек tray-приложения или фиксированного значения 1.

| Код response `[8]` | Частота |
| ---: | ---: |
| 1 | 1000 Гц |
| 2 | 2000 Гц |
| 3 | 4000 Гц |
| 4 | 8000 Гц |

На реальном приёмнике `PID_EB01` 2026-11-16 получено 1000 Гц; значение
совпало с настройкой NinjaForce, которую подтвердил владелец. Повторные
чтения вернули тот же результат. Остальные коды сверены с интерфейсом
производителя и покрыты тестами, но настройка частоты на устройстве не менялась.

Важно:

- Это настроенная частота активного профиля, не измерение потока событий
  движения и не вывод из USB `bInterval`.
- Частота читается из того же интерфейса, что и заряд. Она не подменяется
  значением из другого подключения или предыдущего опроса.
- Неверный report ID/echo, неподдерживаемая команда и неизвестный код
  не превращаются в 0 Гц или частоту по умолчанию. Бейдж скрывается,
  корректный заряд продолжает отображаться.
- Для offline-мыши частота не запрашивается и не отображается.
- Команды записи `setRepRate` (`0x05`) и `setPrf` (`0x0F`) не используются.
  Сам вызов `HidD_SetFeature` здесь только передаёт getter-запрос, как и для заряда.

## DPI и профили

DPI читается из активного уровня активного профиля и показывается в отдельном
двухстрочном контурном бейдже между зарядом и статусом питания. Крупная надпись
`DPI` задаёт ширину числового значения: оно выровнено вправо и не выходит за
границы надписи даже для 30000. Верх привязан к видимой границе цифр заряда,
а высота 32–34 логических пикселя сохраняет читаемость обеих строк. Рекомендованная
нижняя линия по середине `%` уступает этому минимуму. Нижняя строка содержит
только источник подключения.

Положение и размеры бейджа фиксированы: DPI и бейдж частоты стоят на одной
вертикальной оси. Текст питания занимает отдельную область шириной 104 px.
Текст статуса остаётся привязанным к правому краю этой области. Для `100%`
зарезервировано место без пересечений; однозначный заряд и изменение надписи
питания не двигают DPI. Верхний ориентир также измеряется по `88`, а числовые
показатели используют один шрифт независимо от языка. Размер цифр DPI рассчитывается
по самому широкому пятизначному значению и не меняется между DPI-ступенями.

Getter-последовательность сверена с
`getPrf()`, `getStage()` и `getDpi(stage)` в NinjaForce 1.0.8.

Пример для профиля 1 и уровня 2, включая report ID:

```text
Active DPI stage: 06 1C 00 00 01 00 00 01 00 00 00 00 00 00 00 00
DPI of stage 2:   06 04 00 00 01 00 01 01 02 00 00 00 00 00 00 00
```

В ответе DPI байты `[8]` и `[9]` — little-endian уровень `n`, а DPI Ten равен
`(n + 1) * 50`. Например, `n = 21` соответствует 1100 DPI. Вычисление выполняется
в расширенном типе, чтобы `0xffff` не переполнился в допустимое значение.
Принимается диапазон 100–30000 с шагом 50, соответствующий интерфейсу Ten
в NinjaForce. Для Sora V3 схема другая; переносить этот декодер на неё нельзя.

На реальном приёмнике прочитано 1100 DPI, что совпало с настройкой владельца.
Никаких изменений DPI, профиля или частоты при проверке не выполнялось.
Недопустимый индекс уровня, неизвестный ответ или ошибка чтения скрывают только
DPI. Заряд и частота остаются доступными; сбой частоты тоже не мешает читать DPI.
Команды записи `setDpi` (`0x03`) и `setStage` (`0x1B`) не используются.

Более безопасные варианты исследования:

1. Посмотреть, что отправляет официальный Ninjutso-софт, когда он только открывает или читает страницы профилей.
2. Сравнить feature reports до и после изменения одного DPI-слота в официальном софте.
3. Изучить прошивку или официальные конфиг-файлы на предмет command ID и структуры полей.
4. Добавлять новые команды в этот проект только после понимания, что команда read-only, либо после понимания write-поведения.

Возможная будущая структура в Rust:

```rust
struct DpiProfile {
    slot: u8,
    dpi_x: u16,
    dpi_y: u16,
    color_rgb: Option<[u8; 3]>,
    enabled: bool,
}
```

Первое полезное расширение для разработки - debug-команда, которая печатает raw reports только для явно указанных известных безопасных command ID, например:

```powershell
cargo run -- --raw 0x12
```

Не стоит по умолчанию делать режим вроде `--scan 0x00..0xff`. В vendor HID-протоколах один и тот же feature-report механизм часто используется и для чтения, и для записи настроек.

## Тема карточки и меню

В меню трея доступны `Auto`, `Light` и `Dark` с локализованными названиями.
Предпочтение хранится как `theme=auto|light|dark` в общем файле настроек.
Отсутствующий ключ оставляет прежнее поведение — следовать Windows; неизвестное
значение не сбрасывает другие настройки. В явных режимах тема Windows не влияет
на выбранную палитру. Смена темы обновляет существующую карточку без её пересоздания.
Меню по ПКМ и оба подменю используют ту же палитру; режим «Авто» получает системную
тему из GPUI, как и карточка. При высокой контрастности или включённом системном
режиме экранного диктора меню сохраняет стандартную системную отрисовку.

`crates/core/src/presentation/menu.rs` описывает дерево меню, локализованные подписи,
типизированные команды и отметки выбора без Win32/GPUI. В том же пакете
`presentation/theme.rs` разрешает предпочтение темы и предоставляет общую палитру,
а `application.rs` принимает команды меню как события.
Windows-адаптер `platform/windows/context_menu.rs` отвечает только за нативные меню,
масштабирование и отрисовку через документированные API. Источник системной темы
остаётся за GPUI, а хранение настроек — за контроллером и платформенным хранилищем.
Для будущего Linux-адаптера не нужно дублировать структуру меню, команды или правила
темы; Windows API и числовые идентификаторы команд в общий слой не попадают.

Переносимое ядро выделено в отдельный пакет `ninjutso-battery-core` без внешних
зависимостей и build-скрипта, с `#![forbid(unsafe_code)]`. Контрактные тесты находятся
в `crates/core/tests` и запускаются через `cargo test -p ninjutso-battery-core` без
линковки GPUI/Win32. Desktop-host сохраняет фасад API и платформенные адаптеры.
Оба пакета наследуют версию, минимальную версию Rust и лицензию из workspace.
Это также позволяет проверять Linux-ядро отдельно, не обещая поддержку Linux GUI.

Проверка `tools/smoke-ui.ps1 -CheckThemePersistence` использует отдельный APPDATA
в `target/verification`, проверяет реальные кадры всех трёх режимов и повторный
запуск. Перед этой проверкой нужно закрыть обычный экземпляр приложения из-за
защиты от мультизапуска. Настройки владельца и тема Windows не изменяются.

`tools/smoke-menu.ps1` запускает debug-preview с тестовыми данными, проверяет реальные
кадры меню и подменю в трёх темах на пяти языках, управление стрелками/Enter/Esc,
отметки выбора, освобождение GDI-ресурсов и завершение с открытым меню. Настройки
владельца и HID не затрагиваются; снимки сохраняются только в `target/verification`.

`tools/smoke-ui.ps1 -CheckDpiLayout` дополнительно проверяет пиксели настоящих
снимков: две строки бейджа, размер подписи относительно значения, числовые границы,
правое выравнивание, верхнюю привязку, оптические отступы и общую ось с частотой. Для отсутствующего
DPI проверяется отсутствие устаревшего бейджа. Измерение шрифта и GPUI-вёрстка не
содержат Win32-зависимостей; правила высоты и данные бейджа остаются в core.

## Заметки по tray-части

Приложение создает скрытое Win32-окно и регистрирует tray icon через `Shell_NotifyIconW`.

Важные части:

- `NIM_ADD` добавляет иконку в трей;
- `NIM_MODIFY` обновляет иконку и tooltip после каждого чтения батареи;
- `NIM_DELETE` удаляет иконку при штатном выходе;
- отдельный последовательный HID-reader обновляет данные с интервалом 60 секунд, пока карточка скрыта;
- отдельный timer раз в 650 мс перерисовывает только анимацию зарядки в графическом режиме значка;
- ЛКМ открывает GPUI-карточку с кэшированным состоянием и сразу запрашивает свежее чтение в фоне, не блокируя интерфейс;
- пока карточка открыта, reader использует интервал 1 секунду для заряда, подключения, частоты и DPI; после скрытия возвращается к редкому опросу;
- flyout закрывается повторным кликом по tray-иконке, кликом снаружи или клавишей `Esc`; обычный клик внутри карточки не является скрытой командой закрытия;
- GPUI-карточка позиционируется в рабочей области текущего монитора и обновляется при изменении данных, настроек или темы; анимация tray-иконки не вызывает её перерисовку;
- именованный Windows mutex не позволяет запустить второй обычный экземпляр утилиты; `--once` и debug-preview остаются доступны для диагностики;
- ПКМ открывает контекстное меню через `TrackPopupMenu`;
- пункт `Выход` завершает GPUI и службы чтения/трея; cleanup удаляет таймеры, tray icon и handle иконки;
- пункт `Показать процент` переключает отрисовку цифр поверх значка;
- подменю языка поддерживает `ru`, `en`, `be`, `kk` и `zh-CN`; язык, вариант значка и тема сохраняются в `%APPDATA%\NinjutsoBatteryTray\settings.txt`.

Иконка генерируется в памяти как 32x32 BGRA bitmap и превращается в `HICON` через `CreateDIBSection`, `CreateBitmap` и `CreateIconIndirect`. Отдельный `.ico` файл не нужен. По умолчанию tray-иконка рисует крупные цифры заряда на всю доступную область значка, без символа `%`, чтобы не тратить пиксели. Если режим цифр выключен, иконка рисуется как упрощенный силуэт мыши, корпус которого заполнен цветом уровня заряда. Точный процент со знаком `%` вынесен в popup и tooltip. При зарядке поверх реальной заливки рисуется движущаяся светлая полоса; фактический процент при этом не меняется до следующего HID-опроса.

Иконка самого `.exe` устроена отдельно от tray-иконки. `build.rs` генерирует multi-size `.ico` и минимальный `.rc`, затем вызывает `rc.exe` из Windows SDK и передает полученный `.res` MSVC-линкеру. Это влияет на иконку файла в проводнике, ярлыках и списках приложений, но не заменяет динамическую tray-иконку.

## Безопасность

Текущая утилита:

- не требует прав администратора;
- не устанавливает kernel-драйверы;
- не перехватывает USB-трафик;
- не внедряется в чужие процессы;
- обращается только к подходящим HID device paths через документированные Windows API.

Это не означает, что любая будущая vendor-команда безопасна. Исследование неизвестных команд лучше держать отдельно от tray-приложения, пока поведение команды не будет понятно.
