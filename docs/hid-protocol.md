# Заметки по HID-протоколу

Этот документ фиксирует проверенное поведение HID, которое использует tray-утилита, и безопасные направления для будущих доработок.

## Область применимости

Проверенные интерфейсы Ninjutso Ten на этой машине:

```text
VID_093A&PID_EB01  беспроводной приёмник
VID_093A&PID_E020  мышь, подключённая по USB (REV_1613)
```

И приёмник, и подключённая по USB мышь видны в системе как составные HID-устройства с несколькими HID-коллекциями. Не каждая коллекция принимает vendor feature report. Поэтому утилита перечисляет все доступные HID-интерфейсы и пробует только пути, содержащие один из проверенных идентификаторов:

```text
vid_093a&pid_eb01
vid_093a&pid_e020
```

На момент проверки рабочая коллекция для батареи выглядела примерно так:

```text
\\?\hid#vid_093a&pid_eb01&mi_02&col06#...\{4d1e55b2-f16f-11cf-88cb-001111000030}
```

Точный instance id между `#` может меняться между машинами, USB-портами, донглами или состояниями спаривания. `mi_02&col06` полезно воспринимать как подсказку для приёмника, но не как жестко заданный адрес. У проводного `PID_E020` Windows также создаёт несколько vendor-defined коллекций на `MI_02`, поэтому для него действует тот же перебор путей.

## Как устроен доступ через Win32

Rust-приложение использует прямой FFI к стандартным Windows API:

- `HidD_GetHidGuid` из `hid.dll`;
- `SetupDiGetClassDevsW`, `SetupDiEnumDeviceInterfaces`, `SetupDiGetDeviceInterfaceDetailW`, `SetupDiDestroyDeviceInfoList` из `setupapi.dll`;
- `CreateFileW` и `CloseHandle` из `kernel32.dll`;
- `HidD_SetFeature` и `HidD_GetFeature` из `hid.dll`.

HID-путь открывается с такими параметрами:

```text
DesiredAccess: GENERIC_READ | GENERIC_WRITE
ShareMode:     FILE_SHARE_READ | FILE_SHARE_WRITE
Disposition:   OPEN_EXISTING
Attributes:    FILE_ATTRIBUTE_NORMAL
```

Некоторые подходящие HID-пути возвращают `Access denied` или `Invalid function`. Для составных HID-устройств это нормально. Текущая реализация пробует найденные пути по очереди, пока один из них не вернет ожидаемый echo команды.

## Формат feature report

Все проверенные команды используют 16-байтовый feature report.

Буфер запроса перед `HidD_SetFeature`:

| Индекс байта | Значение | Смысл |
| --- | --- | --- |
| `[0]` | `0x06` | HID report ID |
| `[1]` | command | vendor-команда |
| `[2]` | `0x00` | не используется в проверенных командах |
| `[3]` | `0x00` | не используется в проверенных командах |
| `[4]` | `0x01` | request marker, который ожидает устройство |
| `[5..15]` | `0x00` | не используется в проверенных командах |

Последовательность чтения:

1. Заполнить 16-байтовый буфер запроса.
2. Вызвать `HidD_SetFeature(handle, request, 16)`.
3. Подождать примерно 30 мс.
4. Заполнить 16-байтовый буфер ответа нулями и поставить `response[0] = 0x06`.
5. Вызвать `HidD_GetFeature(handle, response, 16)`.
6. Проверить, что `response[1] == command`.
7. Читать полезное значение из `response[8]`.

В проверенных battery reports также встречался `response[6] = 0x01`, но текущая утилита на этот байт не опирается.

## Проверенные команды

| Команда | Decimal | Смысл | Текущий парсер |
| --- | ---: | --- | --- |
| `0x11` | 17 | статус зарядки | `response[8] != 0` |
| `0x12` | 18 | процент заряда | `response[8]`, ожидаемо `0..=100` |
| `0x13` | 19 | online-статус | `response[8] == 1` |

Текущий путь в Rust-коде:

```text
read_mouse_battery()
  enumerate_hid_paths()
  сначала пробует PID_E020 (USB), затем PID_EB01 (приёмник)
  query_battery_path(path, connection_kind)
    query_feature(path, 19) -> online
    query_feature(path, 18) -> battery percent
    query_feature(path, 17) -> charging state
```

Проводной интерфейс проверяется первым, потому что при одновременно вставленном приёмнике USB-подключение даёт наиболее прямое состояние мыши. Если рабочий report отвечает, но `online == false`, результат сохраняется как fallback; утилита продолжает искать online-интерфейс.

## Пример сырых ответов

Снято 2026-07-04 при заряде 93%, мышь online, не заряжается:

```text
Online:  06 13 00 00 00 00 01 00 01 00 00 00 00 00 00 00
Battery: 06 12 00 00 00 00 01 00 5D 00 00 00 00 00 00 00
Charge:  06 11 00 00 00 00 01 00 00 00 00 00 00 00 00 00
```

Расшифровка:

- `0x13` вернулась echo в байте `[1]`, байт `[8] = 0x01`, значит мышь online;
- `0x12` вернулась echo в байте `[1]`, байт `[8] = 0x5D`, decimal `93`, значит заряд 93%;
- `0x11` вернулась echo в байте `[1]`, байт `[8] = 0x00`, значит зарядка не идет.

## Проверка проводного режима

Снято 2026-07-16 при подключении Ninjutso Ten кабелем:

```text
PID:       E020
Battery:   100%
Online:    true
Charging:  true
```

Установленный NinjaForce 1.0.7 был дополнительно проверен как источник протокола. В его ресурсах `57376` (`0xE020`) указан среди проводных PID, а чтение заряда, процента и online-статуса выполняется теми же командами `17`, `18` и `19` с полезным значением в байте `[8]`. То есть поддержка USB в tray-утилите использует штатный read-only путь устройства, а не неизвестную vendor-команду.

## DPI и профили

DPI-профили пока не размечены. Не стоит брутфорсить неизвестные значения command против мыши, если нет готовности рискнуть изменением настроек.

Более безопасные варианты исследования:

1. Посмотреть, что отправляет официальный Ninjutso-софт, когда он только открывает или читает страницы профилей.
2. Сравнить feature reports до и после изменения одного DPI-слота в официальном софте.
3. Изучить прошивку или официальные конфиг-файлы на предмет command ID и структуры полей.
4. Добавлять новые команды в этот проект только после понимания, что команда read-only, либо после понимания write-поведения.

Возможная будущая структура в Rust:

```rust
struct DpiProfile {
    slot: u8,
    dpi_x: u16,
    dpi_y: u16,
    color_rgb: Option<[u8; 3]>,
    enabled: bool,
}
```

Первое полезное расширение для разработки - debug-команда, которая печатает raw reports только для явно указанных известных безопасных command ID, например:

```powershell
cargo run -- --raw 0x12
```

Не стоит по умолчанию делать режим вроде `--scan 0x00..0xff`. В vendor HID-протоколах один и тот же feature-report механизм часто используется и для чтения, и для записи настроек.

## Заметки по tray-части

Приложение создает скрытое Win32-окно и регистрирует tray icon через `Shell_NotifyIconW`.

Важные части:

- `NIM_ADD` добавляет иконку в трей;
- `NIM_MODIFY` обновляет иконку и tooltip после каждого чтения батареи;
- `NIM_DELETE` удаляет иконку при штатном выходе;
- `WM_TIMER` запускает обновление раз в 60 секунд;
- отдельный timer раз в 650 мс перерисовывает только анимацию, если последний известный статус `charging`;
- ЛКМ по tray-иконке перед открытием перечитывает батарею и переключает отдельный локализованный flyout с крупным процентом, источником подключения и статусом зарядки;
- пока flyout открыт, отдельный timer раз в секунду обновляет батарею и источник подключения; после закрытия частый опрос останавливается;
- flyout закрывается повторным кликом по tray-иконке, кликом снаружи или клавишей `Esc`; обычный клик внутри карточки не является скрытой командой закрытия;
- flyout рисуется через двойной буфер, позиционируется в рабочей области текущего монитора и не перерисовывается при каждом кадре анимации tray-иконки;
- именованный Windows mutex не позволяет запустить второй обычный экземпляр утилиты; `--once` и debug-preview остаются доступны для диагностики;
- ПКМ открывает контекстное меню через `TrackPopupMenu`;
- пункт `Выход` вызывает `DestroyWindow`, после чего cleanup удаляет таймер, tray icon и handle иконки;
- пункт `Показать процент` переключает отрисовку цифр поверх значка;
- подменю языка поддерживает `ru`, `en`, `be`, `kk` и `zh-CN` и вместе с настройкой процента сохраняется в `%APPDATA%\NinjutsoBatteryTray\settings.txt`.

Иконка генерируется в памяти как 32x32 BGRA bitmap и превращается в `HICON` через `CreateDIBSection`, `CreateBitmap` и `CreateIconIndirect`. Отдельный `.ico` файл не нужен. По умолчанию tray-иконка рисует крупные цифры заряда на всю доступную область значка, без символа `%`, чтобы не тратить пиксели. Если режим цифр выключен, иконка рисуется как упрощенный силуэт мыши, корпус которого заполнен цветом уровня заряда. Точный процент со знаком `%` вынесен в popup и tooltip. При зарядке поверх реальной заливки рисуется движущаяся светлая полоса; фактический процент при этом не меняется до следующего HID-опроса.

Иконка самого `.exe` устроена отдельно от tray-иконки. `build.rs` генерирует multi-size `.ico` и минимальный `.rc`, затем вызывает `rc.exe` из Windows SDK и передает полученный `.res` MSVC-линкеру. Это влияет на иконку файла в проводнике, ярлыках и списках приложений, но не заменяет динамическую tray-иконку.

## Безопасность

Текущая утилита:

- не требует прав администратора;
- не устанавливает kernel-драйверы;
- не перехватывает USB-трафик;
- не внедряется в чужие процессы;
- обращается только к подходящим HID device paths через документированные Windows API.

Это не означает, что любая будущая vendor-команда безопасна. Исследование неизвестных команд лучше держать отдельно от tray-приложения, пока поведение команды не будет понятно.
